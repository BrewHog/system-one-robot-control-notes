Verify this record

How to independently confirm what these files contain and when they existed.

Do not take my word for any of this. Everything needed to check it is in this directory. The steps below take about two minutes and require nothing from me.

Step 1 — do the files match the manifest?

shasum -a 256 -c manifest.txt      # macOS
sha256sum -c manifest.txt          # Linux

Expected: one OK per file and no FAILED lines. The manifest lists 26 files: the published pages, the raw evidence they cite, and the source code that produced the evidence.

If any line says FAILED, the content has changed since the manifest was generated and you should distrust that file. manifest.txt cannot appear inside itself, so the two proofs in steps 2 and 3 cover its digest directly rather than a separate hash file.

Read the head of the manifest first. It records the digest that was anchored, which you should be able to recompute yourself:

shasum -a 256 manifest.txt

Step 2 — when did those files exist?

manifest.txt was submitted to four independent OpenTimestamps calendar servers, which aggregate many requests into a Merkle tree and commit the root into a Bitcoin transaction. The result is manifest.txt.ots:

pip install opentimestamps-client
ots verify manifest.txt.ots
ots info  manifest.txt.ots      # shows the merkle path and the calendars used

ots info prints the file hash it is proving, which must equal your own shasum -a 256 manifest.txt. If they differ, you are looking at a proof for a different version of the manifest, and the right conclusion is to distrust it rather than to assume a typo. The four calendars used were a.pool.opentimestamps.org, b.pool.opentimestamps.org, a.pool.eternitywall.com and ots.btc.catallaxy.com.

Because a merkle root is only written into a block roughly once per hour, a freshly created proof reports:

Pending confirmation in Bitcoin blockchain

and once a block contains the commitment it reports the block height and time instead. To upgrade a pending proof — no secret key required, only the calendar servers:

ots upgrade manifest.txt.ots
ots verify manifest.txt.ots

Once confirmed, the claim becomes: these exact bytes existed at or before Bitcoin block N. That statement involves no trusted third party. It does not depend on me, on GitHub, on TypeSafe, or on the calendar servers remaining online — only on the Bitcoin blockchain being what it is. Note the asymmetry: the proof is permanent, but converting a pending proof into a confirmed one needs the calendars, so upgrading promptly is worth doing.

Step 3 — a second, independent timestamp

manifest.tsr is an RFC 3161 timestamp token, issued by a commercial Certificate Authority, for the same manifest. It is a separate trust model: a signed, audited assertion of wall-clock time rather than a blockchain commitment.

openssl ts -reply -in manifest.tsr -text

Look for Status: Granted, and confirm the Message data hex block equals your own SHA-256 of manifest.txt. Two independent mechanisms, two different trust models, agreeing on the same digest. Neither required trusting me to state a date.

Rather than printing the serial and time of the current token on this page, compute them yourself — this page is deliberately excluded from the manifest, so the digest does not depend on what is written here:

# Fetch the token details: look for Status: Granted, and read the serial and time.
openssl ts -reply -in manifest.tsr -text | head -20

# The authoritative check is the imprint, not the numbers above:
openssl ts -reply -in manifest.tsr -text | sed -n '/Message data/,+4p'
shasum -a 256 manifest.txt
# The 32 bytes in the Message data block must equal that digest.

This bundle has been re-stamped. The first proofs covered an earlier manifest; two further defects were then fixed (see note 08) and the bundle was re-anchored. The superseded proofs are kept rather than overwritten, because a superseded proof is what establishes that the earlier, weaker claim existed when it claims to have existed:

manifest.txt.ots              current OpenTimestamps proof (pending; upgrade to confirm)
manifest.txt.ots.superseded   proof for the previous manifest - verifies only against it
manifest.tsr                  current RFC 3161 token
manifest.tsr.superseded       token for the previous manifest

A superseded proof will report File does not match original when verified against the current manifest. That is correct behaviour, and is why both are kept.

Step 4 — third-party archive copies

The two proofs above are the ones I control. Archive copies are a third, independent record, held by organisations with no connection to me, with their own crawl timestamps.

Check for existing snapshots:

# Wayback Machine
https://web.archive.org/web/*/brewhog.github.io/system-one-robot-control-notes/*

# archive.today
https://archive.ph/newest/https://brewhog.github.io/system-one-robot-control-notes/

Honest note on timing. Automated submission to both services was rate-limited from the network this was published from (HTTP 429), so the earliest snapshots may postdate the timestamps above by some hours or days. That is exactly why the Bitcoin and RFC 3161 proofs exist rather than relying on archives: a snapshot proves a page was reachable when a crawler happened to visit, whereas the OpenTimestamps proof fixes content and time without needing anyone's cooperation. If archive snapshots are the evidence you care about, use the manual forms rather than assuming a crawler arrives on its own:

https://web.archive.org/save/     (Save Page Now)
https://archive.ph/               (submit a URL in the form)

Step 5 — check the arithmetic behind the headline claim

The most contestable claim on this site is that the shipped control law cannot escape its deadband. That is not an opinion, it is a division, and you can check it from the published source: 

src/scripts/jev_controller.py      # the control law in question
src/scripts/control_law_diagnosis.py  # the harness that measures it
evidence/control_law_diagnosis.json   # the raw result

The argument: the coarse branch triggers at |error| > 0.5 rad and commands 2.4 × error, saturated at 2.2 rad/s, held for 0.9 s. One hold therefore rotates up to 2.2 × 0.9 = 1.98 rad while the deadband is 0.5 rad wide — roughly 1.98 / 0.5 ≈ 4× overshoot. You can also just read the recorded run: identical poses for five consecutive ticks at maximum commanded rotation.

What none of this proves

  • It does not prove I was first. Nothing can. Ideas in this space are being worked on concurrently by many people, and a timestamp only orders events that were actually published.
  • It does not prove the work is good. It proves the files are these files and existed at that time. Whether the conclusions are right is a separate question that the evidence and the code are there for you to attack.
  • It does not establish priority over unpublished work. Someone who did this earlier and never wrote it down is invisible to timestamps, and that is a limitation of the method, not a claim I can make away.
  • The RFC 3161 token depends on a CA. The Bitcoin anchor does not. That is why both exist and why the blockchain one is the backbone.
