Measuring the System 1 round trip

2026-09-18 · live API, not a simulation of one

The whole thesis rests on one number. If a System 1 judgment takes as long as a frontier model's, there is no point to any of this. So this measurement came before any architecture work.

What was measured

Each call sends a small structured robot state and three typed questions, and measures wall-clock time from the call to the parsed response. Nothing is cached or batched: every tick is a fresh round trip, which is the pessimistic and honest case.

response = client.system_one(
    state=state,
    questions={
        "target":    Choice(instructions="Which waypoint should it be heading to?", ...),
        "wall_risk": Noul(instructions="Is the robot close enough to a wall that driving
                                       forward at full speed risks hitting it ...?"),
        "urgency":   Score(instructions="How much of the available speed should the robot
                                        use ...?",
                           criteria=["crawl or hold position", "move slowly",
                                     "move at moderate speed", "move at full speed"]),
    },
)

The three question types cover the three shapes a reflex judgment takes: a boolean (Noul), a pick-from-fixed-set (Choice), and a position on a defined scale (Score).

A single-question call, measured separately during setup, returned in 252 ms — slower than the three-question median, which is worth flagging rather than hiding: my first measurement was the worst one, and the minimum of a small sample is not the number to quote. Treat the median as indicative of a warm connection, not as a guaranteed latency.

What this does and does not support

Supported: a judgment round trip around 150 ms is fast enough to sit inside a robot control loop. At that rate a reflex decision can be refreshed several times a second, which is the timescale that matters for "is something about to go wrong." The jitter (std dev 28 ms, max 223 ms) is small relative to the deliberate 0.9 s spacing between judgments in my control loop.

Not supported: anything about real-time guarantees. This is a network API, so the tail is governed by the network, and my tail here is only 12 samples deep. A single 223 ms outlier in a control loop with a hard deadline is a different kind of problem from a 223 ms outlier in a loop that re-plans a few times a second, and I have not tested the former.

A structural consequence I did not think through at the time. Because the judgment takes ~150 ms and arrives asynchronously, the reflex loop cannot be "ask, then act." It has to be "act continuously on the last judgment, and refresh in the background." That is exactly how biological reflexes work, and it is the reason the code in note 04 separates a slow judgment loop from a fast actuation loop. Realising this was the main architectural insight of the week.

Latency budget

For the loop as actually built, one tick costs roughly:

StageCost
Pose read over rosbridge< 5 ms
System 1 judgment (3 questions)~146 ms median
Actuation hold at 20 Hz900 ms (deliberate)
Command publish< 5 ms

The model is not the bottleneck. The deliberate 900 ms hold dominates the tick budget, and I chose it: re-judging faster than the robot can physically respond just burns API calls. The model being ~6× faster than the loop period it feeds is exactly the headroom the architecture needs, and it means the reflex layer has room to grow into a tighter loop than the one I built.
