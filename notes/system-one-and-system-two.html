System 1 and System 2, and why robotics needs both

2026-09-18 · Justin (BrewHog)

This is the idea the rest of these notes are testing, written down before I had any measurements, so that the record shows what I expected versus what I got.

The two jobs

A robot doing anything useful is doing two categorically different things at once.

System 2 is deliberation: planning a route, reading a work order, deciding a shelf is the wrong shelf, recovering when something unexpected happens. It is slow, expensive, general, and it is what language models are good at. Calling a frontier model takes seconds and produces paragraphs of reasoning.

System 1 is reflex: is the wall close enough to matter, should I commit to this waypoint or hedge, is this grip slipping. It is fast, cheap, narrow, and it has to happen inside a control loop. If your reflex layer takes two seconds, you do not have a reflex layer; you have a slow deliberator standing where a reflex should be.

The mistake I keep seeing is using one model for both jobs. A frontier LLM in a control loop gives you a robot that stands still while it thinks. A small classifier trying to plan gives you a robot that confidently does something stupid in a novel situation. Neither is a tuning problem. They are structural mismatches.

Why this matters now

The reason the split is suddenly practical rather than aspirational is latency. If a System 1 model can return a typed judgment in a couple hundred milliseconds, then the loop budget for robotic reflex finally closes. That is the claim I wanted to test, and it is a claim about a number, not about vibes. So the first thing I did was measure the number rather than assume it.

The division of labour I settled on

The part of this that took me longest to get right, conceptually, is where the boundary sits. My current answer:

Belongs to the model (System 1)Belongs to code
Judgments that resist a formula: is this risky, is this worth a detour, how much should I commit to the current plan. Exact geometry: heading to target, distance, angle wrapping, arrival tolerance.
Classification of a messy situation into a small decision. Conversion of that decision into wheel commands, and the control law that keeps them stable.
Novel situations where a threshold would be arbitrary. Anything with a correct answer that can be computed, which is most things.

Stated as a rule: if it can be computed, compute it; ask the model only what cannot be computed. Every question I ask the model is a question I could not write a satisfying if statement for.

This is also the split the TypeSafe design guidance points at — typed judgments rather than free text, so the consumer of the answer is code and not a human reading prose. I took that seriously when designing the questions: every question returns a boolean, one of a fixed set of labels, or a position on a defined scale, and nothing else.

What I expected, recorded in advance

  1. The System 1 round trip would be fast enough for a control loop. (Measured: median 146 ms. Confirmed — see note 03.)
  2. The model's judgments would vary sensibly with robot state rather than being noise. (Confirmed, after a detour: I misread the Score scale and clamped a working signal into a constant, then corrected it. The model was discriminating correctly all along. See note 05.)
  3. Wiring the two together would be the easy part, because each layer independently worked. (Wrong. This is where it broke — see note 04.)

Point 3 is the interesting one in hindsight. I had a working transport, a working simulator, and a working model, and the composition still failed. Integration is not the easy part; integration is where the assumptions of each layer get tested against the others, and my assumptions did not survive.
