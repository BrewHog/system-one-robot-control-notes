Working Notes / note 05

What did not work

2026-09-18 · kept deliberately, because this is the useful page

Every failure below is something I actually hit, with the evidence that identified it. I am keeping this page because a log with no failures in it is not a log, it is marketing, and because someone else attempting this will hit the same walls.

1. The control law limit cycle

Broke: the robot turned on the spot for 12 consecutive ticks and closed 0.00 m of distance.

Found by: logging the commanded velocity next to the judgment that produced it. The tell was cmd=(0.00,+2.20) repeated verbatim — an actuator pinned at its saturation limit and never leaving is the signature of a limit cycle, not of a hard problem.

Root cause: a 2.2 rad/s turn cap held for 0.9 s can rotate 1.98 rad, while the deadband it aims at is 0.5 rad wide. Roughly 4× overshoot, so the fine-tracking branch was unreachable. Full analysis in note 04.

Status: resolved later. The rate limit removed the deadlock and produced 1.35 m of forward progress where there was none, but it introduced a settling failure in the last part of the run. Two further defects — the Score clamp in section 2 below, and the missing stall detector in section 3 — were still present when this page was written. With all three removed the loop completes the route: 4/4 waypoints, 0 stall ticks. See note 08.

2. I misread the Score scale and clamped away a working signal

Broke: the urgency channel behaved as a constant. Linear velocity was commanded at maximum for the entire run, so a control input I designed to modulate speed was doing nothing at all.

Found by: sorting the raw returned values and noticing every one sat outside the range I had assumed. Across 12 ticks they were:

2.01  2.07  2.10  2.12  2.13  2.15
2.17  2.24  2.41  2.55

Root cause — mine, not the model's: I assumed a Score always returns 0–1. It does not. The returned score is a position on the level numbers, so it runs from 0 to the top level number, which is len(criteria) - 1. My question had four criteria:

criteria=["crawl or hold position", "move slowly",
          "move at moderate speed", "move at full speed"]

so level 0 is "crawl or hold position" and level 3 is "move at full speed". The valid range was 0–3, and a value near 2.1 means "move at moderate speed". Every number the model returned was correct and on-scale.

My code then did this:

urgency = max(0.0, min(1.0, answers["urgency"]))   # WRONG

which clamped a legitimate 2.1 — level 2, "move at moderate speed" — down to 1.0, whose meaning on this scale is "move slowly". The clamp did not merely lose resolution; it inverted the instruction. And since every value exceeded 1.0, every tick clamped to exactly 1.0 and the channel became a constant. The documented approach is explicit: divide each score by its top level number, len(criteria) - 1, to put it on 0 to 1.

Verified. I re-ran the same question against three contexts and recorded raw scores, normalised values, and full probability distributions (evidence/score_scale_check.json):

Situationrawclampednormalisedconfidence
0.4 m from a wall1.1501.0000.3830.71
mid-floor, 2.5 m clear2.8001.0000.9330.80
open space, 4.0 m clear2.9301.0000.9770.93

The model discriminates across the full range, shifts probability mass from level 1 to level 3 as clearance improves, and reports rising confidence as the situation becomes unambiguous. The judgment was working the entire time. My clamp discarded it.

I published this wrong the first time, and this note records that. My initial write-up said the model "returned values outside its defined range" and implied a possible defect on TypeSafe's side. That was incorrect, and it was the damaging kind of error: a confident explanation that points at someone else's component when the fault lay in three lines of my own arithmetic. I found it by going back to the actual Score documentation instead of trusting my assumption about what a score means. The correction is in the commit history; the original claim is not quietly deleted.

Transferable lesson: when a model's output looks out of range, the first hypothesis should be my own misunderstanding of the contract, not the model's failure to honour it. And when you clamp or normalise a model's output, log the raw value and its distribution, not just the value you derived from it. My decision log recorded only scalar scores, so the distributions — the most informative part of the answer — were lost, and I had to re-measure to recover them.

A second defect this exposed: TypeSafe's guidance is that Score levels should describe concrete situations ("broken feature, but workaround exists") rather than bare degrees ("move slowly"). My four levels are closer to degrees than to situations, which is plausibly why the scores cluster mid-scale instead of separating cleanly. Rewriting each level with example situations, alongside the corrected normalisation, is the next improvement here.

3. No collision awareness, so a wedged robot looks like a working one

Broke: the last five ticks of the run have byte-identical poses — (5.63, 5.11) five times — while the loop kept commanding maximum rotation and reported no problem.

Root cause: the state I send to the model contains position, heading, distance to walls, and distance to waypoints. It does not contain anything about whether the robot is actually able to move. So "I am stuck against something" is not representable in the model's input, and the control loop had no error signal to react to.

Fix direction: add an achieved-versus-commanded velocity term to the state — if the robot is commanded 2.2 rad/s and the measured angular_velocity is 0.0, that is an unambiguous stuck signal and it does not need a model to detect it. This is a good illustration of the division of labour: detecting "commanded but not moving" is arithmetic, so it belongs in code, and only the response to being stuck should go to the model.

4. The amd64 simulator image and the silent rosapi failure

Broke: every connectivity check passed and every introspection tool returned empty. ros-mcp connected successfully to a robot it could see nothing about.

Root cause: the upstream example image is amd64-only, so on Apple Silicon it ran under QEMU with a rosapi that never advertised its services. Discovery by service enumeration returns empty, which is indistinguishable from a robot with no topics.

Fixed by: a native arm64 Jazzy image with rosapi launched explicitly. See note 02.

Technical note for anyone repeating this: linux/arm64 is not an optimisation here, it is a correctness requirement. Emulation did not merely make it slow, it made a service-inventory call return a confident empty answer.

5. Verifying with a screenshot that proves nothing

Broke: my first visual verification was a screenshot of the simulator window showing a short trail. It was captured mid-motion, cropped to the window bounds, and shows a turtle that has clearly moved a little. I could not have told a working run from a failed one with it.

Fixed by: reading pose over an independent rosbridge connection and comparing before/after numerically. The screenshot became a supplement — nice for a human, worthless as evidence. Any claim in these notes rests on a numeric before/after, never on an image.

Things I have not tested at all

Listed so the boundary of what I know is explicit:

  • No frontier-LLM baseline in the same loop. I have no measurement of how much slower the System 2 approach would actually be here, which is the comparison that would make the latency argument concrete.
  • No real hardware. Everything is turtlesim, which has no dynamics, no sensor noise, no actuator lag and no safety surface.
  • No test of what happens when the API is slow or unavailable mid-motion. The control loop has no fallback if a judgment never arrives.
  • No notion of safety at all. A reflex layer with write access to cmd_vel and no independent limiter is not something to put near hardware, and I would not.
  • Small samples throughout — 12 ticks, 10 ticks. Enough to find a limit cycle, nowhere near enough for a latency claim.
