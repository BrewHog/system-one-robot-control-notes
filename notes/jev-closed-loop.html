Working Notes / note 04

Closing the loop: model judgment, code control law

2026-09-18 · this one failed. The failure is the point.

The architecture

Two loops, running at different rates, communicating through one shared variable.

SLOW LOOP (every ~900 ms)
  read pose -> build structured state -> ask 3 typed questions -> store judgment
                                                                    |
FAST LOOP (20 Hz)                                                   v
  read pose -> compute heading/distance -> combine with stored judgment
             -> publish cmd_vel -> repeat for the length of the hold

The judge loop owns meaning: which waypoint is the current target, whether a wall is a risk, how much speed to commit. The actuation loop owns geometry: heading error, distance, damping, arrival tolerance. The judgment is read repeatedly by the fast loop but only rewritten every 900 ms, so the robot keeps moving on the last judgment while the next one is in flight.

The three questions

QuestionTypeAnswers in run
Which waypoint should it be heading to? Choice always north-east shelf (consistent, never flip-flopped)
Is the robot close enough to a wall that driving forward at full speed risks hitting it within about one second? Noul 0.20 – 0.30 (never crossed the 0.6 intervention threshold)
How much of the available speed should the robot use? Score 2.01 – 2.55 (see below)

The target question was stable across all 12 ticks, which is a good sign: the model was not thrashing between waypoints. The wall-risk answers were sensibly low and varied with position, which is what you want from a boolean judgment.

The result: 0.00 m of progress

Twelve ticks. Pose start (5.54, 5.54), pose end (5.63, 5.11). Net displacement from origin: 0.36 m. From the second tick onward the commanded velocity was:

Zero linear velocity, angular velocity pinned at its 2.2 rad/s cap, and the distance to the target slowly increasing. The robot turned on the spot for eleven consecutive seconds. Its pose for the last five ticks is byte-identical — (5.63, 5.11) every time — so it ended up wedged and stationary while the loop happily kept commanding maximum rotation.

Diagnosis: not a model bug

The model did nothing wrong. It picked a sensible target, kept picking it, and reported low wall risk. The bug is entirely in my control law, and it is arithmetic:

if abs(error) > 0.5:            # coarse re-orientation deadband (rad)
    linear = 0.0                # stop translating while turning
    angular = clamp(2.4 * error, -2.2, 2.2)

With --hold 0.9 s and angular saturated at 2.2 rad/s, one hold can rotate the robot by up to 1.98 rad. The deadband it is trying to enter is 0.5 rad wide. The controller therefore overshoots the target heading roughly four times over, flips the sign of error, and re-enters the same branch pointing the other way. It cannot ever reach the fine-tracking branch, because that branch requires an error smaller than what one coarse step can jump across. It is a limit cycle, and its signature is exactly what the log shows: constant ±2.20 forever.

The gains were individually reasonable. Coarse deadband of 0.5 rad and a proportional gain of 2.4 are both defensible in isolation. The bug only exists in their relationship to the hold duration — which is to say, in the composition of two layers that each looked fine on their own.

The fix, tested against the bug

I wrote a separate harness, scripts/control_law_diagnosis.py, that replays the shipped law and a rate-limited variant against the same starting pose, so the comparison is controlled rather than anecdotal. The variant keeps the identical architecture and changes only the turn envelope:

# Shipped: gain 2.4, capped at 2.2 rad/s, deadband 0.5 rad.
# Fixed:   never command more than half the remaining error per hold,
#          so the deadband physically cannot be jumped across.
angular = clamp(0.5 * error / hold, -2.2, 2.2)
# ...and creep forward while turning, so a target behind the robot
# cannot produce a rotation-without-translation deadlock.
linear = min(linear, 0.6)

Twelve ticks each, identical start pose (scripts/control_law_diagnosis.py, published as evidence/control_law_diagnosis.json). The shipped law closes exactly nothing — its pose at the end is its pose at the start. The rate-limited law closes 1.35 m.

Do not read that 1.35 m as a fix. The last column is the problem. Over the final window of the run the rate-limited robot moved backwards by 0.46 m, and its tail heading error (2.26 rad) is worse than the shipped law's (1.11 rad). It escapes the deadlock and travels, then loses the plot at the end. The rate limit trades being stuck for being unstable, which is a different bug rather than no bug. My own harness counts the run a failure, and I have left the harness doing so: it prints no improvement measured - do not claim a fix, because closing distance overall is not the same as controlling the robot.

So the honest summary of the fix is: it resolves the rotation deadlock and delivers forward progress, and it introduces a settling failure I have not solved. A proper turn-then-drive controller with an explicit settle phase is the correct next step, and I have not built it. I am also not certain the rate limit is even the right shape of solution — it may just be delaying the same limit cycle at a longer period.

What the failure actually establishes

Three things, and they are the reason I am publishing a failed run rather than quietly fixing it and posting a success:

  1. The layers do compose. State got from the simulator to the model, and a model judgment got back into a live actuation loop. Every hop worked. What broke was my arithmetic, not the integration.
  2. The model's output was usable. A stable target choice and a plausible risk judgment arrived in a median of 146 ms. Nothing about the failure implicates the System 1 layer.
  3. The architecture localised the bug. I knew within one run that the fault was in the control law and not the model, because the decision log records every judgment alongside the command it produced. That auditability is a property of the architecture, and it is a real argument for keeping judgment and actuation in separate layers rather than letting one component do both.
