The two defects that were left

1. The Score clamp, finally removed

Note 05 identified that a Score runs from 0 to len(criteria) - 1, not 0 to 1, and that clamping the raw value to 1.0 had inverted the meaning of the answer. That diagnosis was correct, but the clamp was still in the control loop when notes 04 and 05 were published. The urgency channel was therefore still dead: every tick clamped to exactly 1.0.

The fix is the documented one — divide by the top level number — and it is now applied at a single named site with the raw value preserved alongside it:

URGENCY_TOP_LEVEL = len(QUESTIONS["urgency"].criteria) - 1   # = 3

def normalize_score(raw: float, top_level: int = URGENCY_TOP_LEVEL) -> float:
    """Put a Score on 0..1 the documented way: divide by its top level number."""
    return max(0.0, min(1.0, raw / top_level))

The channel is alive now. Raw scores across the run ranged 1.66–2.94, normalizing to 0.55–0.98, and the commanded speed tracked them. That is the behavior the input was designed for and it was absent in every earlier run.

The related lesson from note 05 is now enforced in the log: both the raw score and the distribution are recorded, not just the derived number. The clamp was invisible precisely because the log held only the value the clamp produced.

2. Stall detection, because it is arithmetic

Note 05 recorded the wedged-robot case: five ticks of byte-identical pose while the loop commanded full rotation and reported nothing wrong. The state sent to the model describes position, heading and clearances, so "I am commanded to move and am not moving" was not representable in it and nothing downstream could react.

Comparing commanded against measured velocity needs no judgment, so it lives in code. Each tick the fast loop accumulates commanded and achieved velocity from /turtle1/pose and flags a stall when the achieved value is under 15% of commanded for a meaningful command:

if cmd_lin > 0.3 and got_lin < 0.15 * cmd_lin:
    stalled = True
if cmd_ang > 0.5 and got_ang < 0.15 * cmd_ang:
    stalled = True

The detected condition is recorded per tick in the decision log. In this run it fired 0 times out of 32, which is the correct answer for a run that completed. It is a detector, not yet a recovery policy — the response to being stuck is the part that should go to the model, and that is not built.

What is still not done

The boundary of what this record supports, unchanged from note 05 except where stated:

  • No frontier-LLM baseline in the same loop. The System 1 / System 2 latency comparison remains unmeasured, and it is the comparison that would make the argument concrete.
  • No stall recovery. Detection exists; response does not.
  • No real hardware. turtlesim has no dynamics, no sensor noise and no actuator lag.
  • No fallback if a judgment never arrives. The loop blocks on the network call.
  • No safety layer. Unguarded write access to cmd_vel.
  • Small samples. 32 ticks, one route. Enough to show convergence and the absence of the limit cycle; nowhere near enough for a latency claim.
  • The Noul wall-risk channel was never exercised. It stayed at 0.15–0.48 for the whole run, so its 0.6 intervention branch never fired and its behavior under load is untested.
  • Thresholds are still demo values. wall_risk > 0.6, ARRIVE_RADIUS = 0.6, DOCK_RADIUS = 0.25 were chosen to make the run work, not calibrated against outcomes.

Related fixes in this pass

Two changes to how the questions are written, both following the documented guidance that levels should describe situations rather than degrees:

  • The four urgency levels were rewritten from bare degrees ("move slowly") to concrete situations ("the robot has an obstacle or a wall within about one metre ahead and should creep").
  • The target Choice instructs the model to prefer waypoints in not_yet_reached, and to hold its current target until it is reached. Code applies hysteresis on top, so a switch is only honoured when the current target is finished or the new pick is strictly closer.
