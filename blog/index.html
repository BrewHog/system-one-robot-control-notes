Coupling a System 1 model to a real robot control loop

Working notes. Raw logs, measured latencies, and the code that produced them.

Started 2026-09-18 · Last updated 2026-09-18 · Justin · github.com/BrewHog

What this is

These are my lab notes from a line of experiments I started in September 2026. The question I am chasing is narrow and specific:

Can a System 1 model — one that returns a typed judgment in a couple hundred milliseconds rather than a paragraph of reasoning in several seconds — drive a robot control loop that a frontier LLM is simply too slow to close? And if so, what is the correct division of labour between the model and ordinary code?

I am not claiming this is a new idea. The System 1 / System 2 split for robotics is talked about openly, and people far better resourced than me are working on it. What I am doing is publishing a dated, reproducible record of my own work on it — the architecture I picked, the numbers I measured, and the failures — so that the record of when I did it exists independently of me.

Three things had to be true before this was worth writing down, and all three are now demonstrated on the machine this was written on:

  1. An LLM client can drive a simulated robot through an MCP server, end to end.
  2. A System 1 model answers typed robotics questions over a live API, fast enough to sit inside a control loop.
  3. The two compose — the model's judgment changes the robot's behaviour, and the decision log proves which judgment caused which movement.

Closed loop Model judgment → control law → continuous actuation, 12 ticks FAIL — robot spun in place, 0.00 m net progress

The headline result is a failure, and I am leaving it in. The individual layers all work: the simulator answers, MCP drives it, and the System 1 model returns a usable judgment in a median of 146 ms. But when I wired them into a closed loop, the robot turned on the spot for the entire trial and made zero net progress. The cause is a bug in my control law, not in the model — and finding that out is the most useful thing this experiment produced. Details in note 04 and note 05.

Repositories and prior work

This work stands on other people's open source, and I want the attribution to be unambiguous:

  • ros-mcp-server — the MCP server that exposes ROS topics and services as tools. Contoro's project; I run it unmodified and drive it from my own client code.
  • ROS 2 Jazzy + turtlesim — the simulated robot body.
  • TypeSafe / JEV — the System 1 model. Documentation at docs.typesafe.ai. I am an early-access user; everything I publish here is my own measurement work, not their material.
  • OpenTimestamps — Bitcoin-anchored proof that these files existed when I say they did.

What I am not claiming

Stated plainly, because overclaiming is how independent work loses credibility:

  • This is turtlesim, a 2D pedagogical simulator. It is not a real robot, and nothing here proves anything about real-world dynamics, sensor noise, or safety.
  • My sample sizes are small — tens of ticks, not thousands. The latency figures are indicative, not a benchmark.
  • I have not compared against a frontier LLM baseline in the same loop yet. That is the obvious next experiment and it is not done.
  • The architecture I landed on is one reasonable choice among several, not a discovered optimum.

Evidence. Every claim above rests on a file in evidence/ — the per-tick decision log with raw model answers, the closed-loop run log, and the control-law diagnosis. Hashes for all of them are in the SHA-256 manifest.

Proof of time. The manifest is anchored in the Bitcoin blockchain via OpenTimestamps and independently signed by a commercial RFC 3161 timestamp authority.
