Getting a simulated robot under MCP control

2026-09-18 · all timestamps PDT

Goal

Before involving any model in a control loop, I wanted the boring half proven: that an MCP client can drive a simulated robot end to end, with the movement confirmed by something other than the client's own claim of success.

The stack

my client  --MCP(stdio)-->  ros-mcp-server  --rosbridge(ws)-->  turtlesim
                                                                    |
                                       independent pose read <-------+
                                       (2nd rosbridge connection)

The important detail is the second connection. A tool that reports "command sent" has proven nothing about whether the robot moved. So the test publishes velocity commands through MCP and then reads /turtle1/pose over a separate WebSocket connection, so the verification path shares no code with the command path.

The ARM64 problem that cost me an evening

The upstream example image for turtlesim is amd64-only. On Apple Silicon that means QEMU emulation, which is far too slow to be useful for anything real-time, and worse, its rosapi node never advertised its services. Since ros-mcp's discovery tools work by asking rosapi what exists, the server connected successfully and could see nothing. That failure mode is genuinely confusing: every connectivity check passes and every introspection call returns empty.

The fix was a native arm64 image built on a Jazzy base with rosapi launched explicitly, rather than relying on the example's launch arrangement. Two consequences worth recording: the emulation problem and the discovery problem had the same root cause, and "it connected" is not the same as "it can see anything."

Result

The end-to-end test passes, and it passed identically on three separate runs — the simulated robot always moves 1.613 m and rotates 1.613 rad, because the test drives a fixed velocity script for a fixed duration. From the published run log (evidence/mcp_e2e_test_output.txt):

Worth noting what does not match between runs: the absolute start pose, because the robot keeps whatever position the previous experiment left it in. The delta is what repeats exactly, which is the correct thing to check — a test that verified absolute position would be flaky and one that reported only "success" would prove nothing.

Verdict: the transport layer works. An MCP client can drive a simulated robot, and the movement is confirmed by an independent read rather than by trusting the tool's return value.

Why the 31 tools matter

Those tools are the model's entire action space. This is the part that makes the architecture plausible: the agent does not get a bespoke API I designed for it, it gets the same ROS surface a human engineer would use — publish, subscribe, call service, read parameters. Anything that can be done through rosbridge is available to the model without new integration work.

It is also, in retrospect, a large action space for a System 1 reflex layer to be pointed at. In the closed-loop experiment I deliberately narrowed it to a single cmd_vel publish, because reflex is not the place for a model choosing among 31 verbs.
